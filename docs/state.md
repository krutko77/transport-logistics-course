## Сейчас в работе
- **2026-09-20: НОВОЕ — реальные письма с результатами теста не приходят
  ВООБЩЕ, даже в спам.** Отличается от истории ниже: диагностические
  curl-запросы напрямую к UniSender Go доходили (пусть и в спам), но при
  реальном прохождении теста через сайт письмо не появляется нигде.
  Добавили временный эндпоинт `GET /api/debug-env` (только true/false по
  ключевым переменным, без раскрытия секретов) — задеплоили, пользователь
  открыл в браузере (curl с этого контейнера на свой домен зависает,
  известный анти-loopback файрвол). **Результат: ВСЕ переменные окружения
  на сервере пустые** — `MANAGER_EMAIL`, `UNISENDER_GO_API_KEY`,
  `UNISENDER_GO_USER_ID`, `UNISENDER_GO_API_URL`, `UNISENDER_GO_FROM` все
  `false`. Повторный деплой через `vibe-deploy-service` не исправил —
  переменные остались пустыми после повторной проверки. Эндпоинт
  `/api/debug-env` удалён из кода после диагностики (это был временный
  диагностический код, не оставлять в проде).
  **Вывод:** `.env` проекта либо не копируется на сервер при rsync-деплое,
  либо pm2-процесс запускается без него — код `results.js` и
  `mailer.js` при этом работает правильно (проверено ранее прямым curl
  с реальными значениями из `.env`), просто на сервере ему неоткуда взять
  значения. `if (process.env.MANAGER_EMAIL)` в `results.js` в этом случае
  молча пропускает отправку письма без единой ошибки — отсюда и полное
  отсутствие письма даже в спаме.
  **Это инфраструктурная проблема `vibe-deploy-service`, не код проекта.**
  Агент не может её починить без SSH-доступа к серверу — нужно обратиться
  к администратору портала с просьбой проверить, копируется ли `.env`
  файла проекта при деплое и передаётся ли он в pm2-процесс.

- **2026-09-20 (более ранняя часть той же сессии): письма уходят, но
  попадают в СПАМ — причина найдена.**
  Сотрудник прошёл тест повторно — письмо снова не появилось во
  «Входящих» на kpv@es-trans.pro. Диагностика:
  1. Прямой curl к UniSender Go API с текущим ключом отработал успешно
     (`status: success`) — API-контракт (`X-API-KEY` в заголовке) исправен,
     не является причиной.
  2. Проверили личный кабинет UniSender Go: домен отправки `es-trans.pro`
     — подтверждён, DKIM настроен. Домен ссылок `unisender.es-trans.pro`
     — в статусе "Настроен". Оба не являются причиной.
  3. Письмо нашлось в папке СПАМ на kpv@es-trans.pro. Разобрали заголовки
     (`X-Spam-Report` от Rspamd на стороне timeweb): `SPF`, `DKIM`, `DMARC`
     все проходят (`R_SPF_ALLOW`, `R_DKIM_ALLOW`, `DMARC_POLICY_ALLOW`).
     **Главный вклад в спам-балл (10.4, порог обычно ~7) —
     `URIBL_BLACK(7.50)`**: один из URL в письме (вероятнее всего ссылка
     `List-Unsubscribe` на `unisender.es-trans.pro` или инфраструктурный
     домен UniSender `themailer.ru`/`msgpanel.com` в цепочке `Received`)
     находится в чёрном списке URIBL, который использует почтовый сервер
     timeweb. Остальные символы (`BAYES_SPAM 1.60`, `CTYPE_MIXED_BOGUS
     1.00`, `FORGED_SENDER 0.30` и т.д.) вносят по мелочи и сами по себе
     ниже порога.
  **Вывод:** это не баг кода проекта и не настройка UniSender — это
  занесение домена/URL в чёрный список на стороне почтового сервера
  получателя (timeweb). **Дальнейшие действия — вне зоны агента:**
  пользователь договорился написать администратору timeweb/почты
  `es-trans.pro` с просьбой добавить в белый список (whitelist) домены
  `unisender.es-trans.pro`, `themailer.ru`, `msgpanel.com`, либо
  скорректировать/отключить правило `URIBL_BLACK` для писем от
  `noreply@es-trans.pro`. Приложить пример заголовков письма (см. выше)
  как доказательство. Код и деплой проекта менять не требуется.
  **2026-09-20, попытка исправить со стороны кода:** вместо обращения к
  администратору сначала попробовали убрать сами ссылки, вызывающие
  URIBL_BLACK. В `src/services/mailer.js` в тело запроса к
  `email/send.json` добавлены `skip_unsubscribe: 1` (отключает
  автоматически добавляемую UniSender Go ссылку отписки/`List-Unsubscribe`)
  и `track_links: 0` (отключает подмену ссылок в письме на трекинговые
  через `unisender.es-trans.pro`). Письмо не содержит собственных ссылок,
  поэтому после этой правки в письме не должно остаться URL вообще.
  Нужно передеплоить и проверить: пройти тест → письмо должно попасть во
  «Входящие», не в СПАМ. Если не поможет — тогда обращаться к
  администратору timeweb/почты с текстом выше.
