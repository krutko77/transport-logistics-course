**2026-09-20: обнаружен и исправлен баг доставки писем.** Пользователь
прошёл тест — письмо на `kpv@es-trans.pro` не пришло. Диагностика прямым
curl к UniSender Go показала: передача `apiKey`/`user_id` в теле JSON (как
было реализовано в `src/services/mailer.js` и задокументировано в
CLAUDE.md) возвращает `code 101: API key is missing`. Ключ нужно
передавать в заголовке `X-API-KEY`; `user_id` при этом не требуется.
Исправлено в `mailer.js` и в CLAUDE.md, задеплоено. **Предыдущее
"подтверждено эмпирически через тестовый запрос в личном кабинете
UniSender" (см. историю ниже) было ошибочным или устарело** — вывод не
проверялся повторно с момента первого внедрения. Само письмо, отправленное
диагностическим curl-запросом, ушло успешно (`status: success`) — стоит
уточнить у пользователя, дошло ли оно и дошло ли обычное письмо через
починенный `mailer.js` после деплоя.

**2026-09-20: тот же баг исправлен и в соседних проектах.** Тот же паттерн
"ключ в теле JSON" был скопирован в `es-trans_test_GFD_MOO` (test-1) и
`es-trans_test_standard_MOO` (test-2) — исправлен там же (`mailer.js` +
CLAUDE.md), оба проекта задеплоены. `es-trans_test_GFD_MOO` — гит-репозиторий
без настроенного remote (закоммичено локально, пуш не требуется/невозможен).
`es-trans_test_standard_MOO` — не гит-репозиторий вовсе, изменения только на
диске, подхвачены деплоем через rsync. Сквозная проверка (реальное
прохождение теста → письмо руководителю) в этой сессии не делалась ни для
одного из трёх проектов — стоит попросить кого-то пройти каждый тест и
подтвердить получение письма.

Конфликт доменов `test-1`/`test-2` у соседних проектов
`es-trans_test_GFD_MOO` и `es-trans_test_standard_MOO` снят
